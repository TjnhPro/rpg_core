# RPG Core v2.0.0 release notes

Status: release candidate; transition implementation authorized, Gate B pending.
No release tag or GitHub Release exists as part of this candidate preparation.

## Accepted architecture

Developer decision `RPG_CORE_V2_ARCHITECTURE_ACCEPTED` activates Architecture
Freeze v2.0 at `e99d36e4345e14486ec40448ad8df872d3a44a57`. PR #6 merged without
squashing at `cc7affbcc01decd1fda9ec4b0d7f9f55ba3fda87`, preserving acceptance
provenance. The [original manifest](../v2/2.0.12-architecture-freeze.json) remains
PROPOSED as the immutable historical review artifact. All eight original section
hashes and the [accepted evidence](../v2/2.0.12-architecture-closure-evidence.json)
remain unchanged.

Kernel owns canonical numerical implementations and contracts. Legacy owns
gameplay validators, eligibility, Skills, Combat, Mechanics, Effects, Triggers,
resource commits and events. Applications own game rules/content, configuration,
assets, clocks/RNG and orchestration. Kernel never depends on Legacy/gameplay.

## Compatibility and installation

Package `@rpg/core@2.0.0` is private and native ESM. Node >=22.13.0 is required
for verification; CommonJS is not provided. All eleven public entrypoints remain
available. Kernel retains 63 public symbols / 17 runtime APIs; Legacy root retains
243 symbols / 122 runtime values. Kernel is independently importable from
`@rpg/core/kernel`. The Legacy root retains its established surface.

```sh
npm ci --ignore-scripts
npm pack
# From the application, use the actual archive path:
npm install /path/to/rpg-core-2.0.0.tgz
```

See [README usage](../../README.md#install-and-public-api). Package contents remain
dist, README, VERSION, historical EXPORT-MANIFEST and package metadata; release
documentation is repository/GitHub documentation and is not added to the archive.
No dependency, export or compiler-configuration changes accompany the version bump.
No npm publication or license grant is included.

Text RPG (9), Võ Lâm-style 2.5D (10) and ARPG-inspired (13) independent consumers
verify 32 numerical scenarios, all 17 Kernel APIs and caller-owned policies.
61 Legacy isolation scenarios retain RNG, resource/action/event and Root/Child/
Trigger observations. This is finite scenario evidence, not complete game support
or an assertion of commercial-game formula equivalence.

## Release verification checklist

Before Gate B: build/typecheck, architecture/preservation, targeted regression,
historical mode, actual release mode and one fresh installed 2.0.0 artifact.
Report [transition evidence](v2.0.0-transition-review.md); stop for Developer review.

```sh
node scripts/review-release-transition.mjs --historical
npm run build
npm run typecheck
npm run check:architecture
npm run check:preservation
npm run test:consumer > .git/release-installed.log
node scripts/review-release-transition.mjs --release --installed-log .git/release-installed.log
```

Historical mode builds/audits accepted Git source in a temporary detached worktree
using its unchanged lockfile and `npm ci --ignore-scripts`. Use LF checkout bytes
(`core.autocrlf=false`) for historical byte-sensitive forwarders and consumer
provenance. It does not execute the candidate or validate release metadata.
Release mode executes/inspects the current package; it cannot pass using only old
Git blobs. Its exact transition record cannot broaden its own allowed changes.

After Gate B approval: full `npm run verify`, both review modes, `git diff --check`,
review exact metadata diff and zero source/oracle/preservation delta; commit/push
the release branch and open a release PR. Confirm exact-head PR/push Node 22.13.0
and Node 24 CI, then obtain final Developer release approval.

Only after that separate approval: merge the release PR preserving commit mapping,
verify main and exact-head CI, create annotated `v2.0.0` at the approved main release
commit and publish the GitHub Release using these notes and changelog. Verify tag,
commit, package/lock/VERSION alignment and release links. Keep `private: true`;
npm publishing requires separate approval.

## Future changes

Compatible work keeps the accepted owners and relevant regression checks. Missing
numerical capabilities require CORE_CAPABILITY_GAP review. Breaking ownership or
contracts require ARCHITECTURE_CHANGE_REQUEST with alternatives, consumer impact,
migration, verification and rollback. Never rewrite accepted architecture or
preservation to make an unauthorized change pass.
